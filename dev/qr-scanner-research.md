# QR scanner research

Reviewed on 16 November 2026. This report compares source-available decoding engines, browser scanner packages, and Elixir integrations for OpenQR Web. It records the selection rationale and distinguishes source-review findings from validation of the accompanying implementation.

## Recommendation

Use the reader entry point of **zxing-wasm 3.1.7**, with a modest Phoenix LiveView hook owning camera controls and an application-owned worker performing decoding. It has the strongest combined evidence for decoder structure, resource ownership, tests, build portability, and exposed QR features among the inspected browser decoding paths. Its [pinned ZXing-C++ submodule](https://github.com/Sec-ant/zxing-wasm/tree/1a2b5310056a2b140feb6ca625fcefd6eaf12ef0/zxing-cpp), `f19f7c6e0509fe0eeb822bf35c41b0f637dec290`, is exactly the revision already used by the sibling OpenQR native engine. The [reader build](https://github.com/Sec-ant/zxing-wasm/blob/1a2b5310056a2b140feb6ca625fcefd6eaf12ef0/src/cpp/CMakeLists.txt#L15-L97) excludes the writer, and the [reader API](https://github.com/Sec-ant/zxing-wasm/blob/1a2b5310056a2b140feb6ca625fcefd6eaf12ef0/src/reader/index.ts#L13-L30) accepts both image files and pixel data.

This is a source-based fit assessment, not a claim that ZXing recognises every difficult photograph better or runs fastest on every phone. The same decoder revision also means browser scanning and generation verification are related evidence, rather than independent confirmation from different algorithms.

Keep ordinary camera and file scanning in the browser. If server-side file decoding becomes a requirement, expose the decoder already inside OpenQR's native engine through its existing C API and dirty CPU NIF. The current native verifier only checks generated frames against an expected payload, so this requires a new callable decoding operation. Among independently packaged Elixir alternatives, Rxing is the strongest initial candidate, while image_qrcode becomes attractive if Vix is wanted for other image processing.

## Scope and evidence

Discovery covered npm, Hex, GitHub repository searches, targeted web searches, and cross-references found in source dependencies. Hex searches included `qr`, `barcode`, `zbar`, `zxing`, and `evision`. GitHub searches included QR decoding, barcode scanning, ZXing, quirc, and Elixir combinations. Browser discovery included complete scanner applications as well as reusable libraries. This is a broad, bounded search, not an exhaustive catalogue of every repository or commercial SDK.

Only implementation, tests, build definitions, CI configuration, dependency locks, and licence files support the assessments below. Registry metadata located packages and versions. README claims, stars, downloads, reviews, package descriptions, and unsupported assumptions about established project names did not determine scores. An inspected CI definition establishes what it is configured to run, not that the latest run passed.

Pinned source snapshots were inspected for the principal JS, WASM, C, and Elixir candidates. OpenCV and opencv_contrib were sampled through specific source, test, build, and licence files, so their assessment has lower confidence. Package and repository snapshots were pinned separately where release tags were absent. Different revisions of an engine are not credited with each other's improvements.

Three layers need separate comparisons:

| Layer | Responsibility | What a high score does not establish |
|---|---|---|
| Decoder engine or low-level reader | Find symbols, recover payloads, expose positions and metadata, and manage decoding resources | Camera permissions, usable controls, or LiveView lifecycle handling |
| Browser scanner wrapper or application | Own media streams, frame scheduling, UI controls, and decoder selection | A new independent decoding algorithm or equivalent quality across its fallback engines |
| Elixir integration | Accept server-side image input, schedule native work, and package native dependencies | Access to a user's browser camera or low-cost continuous frame transport |

## Scoring

Each criterion receives 1 to 5 points, with an unweighted total out of 30. A score of 1 means little useful evidence or a concrete serious weakness, 2 means partial implementation with substantial gaps, 3 means serviceable evidence with material limits, 4 means strong implementation and supporting evidence, and 5 means the strongest observed evidence for that layer and scope. These are qualitative review judgements, not measured accuracy, latency, memory, or reliability figures. Differences of one point should not be read as precise measurements.

| Code | Criterion | Evidence considered |
|---|---|---|
| A | Architecture | Ownership, separation of decoding from capture, processing flow, and appropriate use of dependencies |
| E | Engineering practices | Behavioural tests, malformed-input handling, resource cleanup, and meaningful build or CI checks |
| M | Maintainability | Dependency and artifact provenance, concrete defects, repeated state, tooling burden, and change impact |
| O | Code organisation | Clear module boundaries, placement of related workflows, and navigable implementation |
| P | Cross-platform support | Portable APIs, native build targets, runtime tests, and browser-specific handling |
| F | Feature coverage | Features actually exposed at that layer, including QR variants, payload modes, multiple results, files, and controls |

P scores describe the breadth of available source and build evidence. They do not mean all browsers, phones, operating systems, CPUs, camera drivers, or hardware combinations were tested. A platform-neutral API can have a strong portability design while still needing device validation. Totals compare candidates within each table, rather than making an Elixir binding and a browser UI interchangeable.

### Why these scores differ

**ZXing-C++ and zxing-wasm.** The [shared recognition flow](https://github.com/zxing-cpp/zxing-cpp/blob/f19f7c6e0509fe0eeb822bf35c41b0f637dec290/core/src/ReadBarcode.cpp#L243-L324) separates image preparation, binarisation, reader selection, and distinct-result accumulation. The [QR reader](https://github.com/zxing-cpp/zxing-cpp/blob/f19f7c6e0509fe0eeb822bf35c41b0f637dec290/core/src/qrcode/QRReader.cpp#L24-L132) contains standard QR, Micro QR, and rMQR paths, although an rMQR detection branch still carries a concrete unfinished-design comment. [Native CI](https://github.com/zxing-cpp/zxing-cpp/blob/f19f7c6e0509fe0eeb822bf35c41b0f637dec290/.github/workflows/ci.yml#L20-L153) configures unit, corpus, installation, and language-binding checks across desktop operating systems and ARM runners, while [fuzzer configuration](https://github.com/zxing-cpp/zxing-cpp/blob/f19f7c6e0509fe0eeb822bf35c41b0f637dec290/test/fuzz/CMakeLists.txt#L11-L31) adds useful malformed-input tooling.

The WASM package uses [finally-based allocation and vector cleanup](https://github.com/Sec-ant/zxing-wasm/blob/1a2b5310056a2b140feb6ca625fcefd6eaf12ef0/src/share.ts#L300-L395), with [memory tests](https://github.com/Sec-ant/zxing-wasm/blob/1a2b5310056a2b140feb6ca625fcefd6eaf12ef0/tests/memory.test.ts#L68-L110) covering deletion on failure and stable copied results. Its [runtime tests](https://github.com/Sec-ant/zxing-wasm/blob/1a2b5310056a2b140feb6ca625fcefd6eaf12ef0/tests/runtime.test.ts#L10-L39) exercise built packages in Node, Bun, and Deno. Module loading is asynchronous, but recognition is synchronous once loaded, and the package starts no worker. [Purging the module cache](https://github.com/Sec-ant/zxing-wasm/blob/1a2b5310056a2b140feb6ca625fcefd6eaf12ef0/src/share.ts#L230-L285) removes a cached promise rather than guaranteeing immediate reclamation of the WASM heap. This is why the recommendation includes an application-owned worker.

The reader build also has a provenance limit: its [stb FetchContent declaration](https://github.com/zxing-cpp/zxing-cpp/blob/f19f7c6e0509fe0eeb822bf35c41b0f637dec290/zxing.cmake#L2-L27) does not pin a revision. The published npm artifact is integrity-locked locally, and the ZXing core revision is known, but the exact stb source revision used for that binary is not established by the inspected build configuration. Shipped notices identify this limit and include the wrapper, native glue, core, bundled character conversion, image codec, and runtime notices.

**zxing-js.** The typed [QR reader](https://github.com/zxing-js/library/blob/1722d0744fb5e8b47aebfbeb2b648e17c95e8595/src/core/qrcode/QRCodeReader.ts#L41-L114) composes detection and decoding cleanly, including mirrored input, raw bytes, ECC, and structured-append metadata. [Micro QR is implemented](https://github.com/zxing-js/library/blob/1722d0744fb5e8b47aebfbeb2b648e17c95e8595/src/core/microqr/MicroQRCodeReader.ts#L31-L76), so describing this candidate as standard-QR-only would be wrong. No rMQR implementation was found, and the inspected QR API returns one result. [Corpus tests](https://github.com/zxing-js/library/blob/1722d0744fb5e8b47aebfbeb2b648e17c95e8595/src/test/core/qrcode/QRCodeBlackBox.1.spec.ts#L27-L43) assert rotation success thresholds. Current [CI](https://github.com/zxing-js/library/blob/1722d0744fb5e8b47aebfbeb2b648e17c95e8595/.github/workflows/ci.yml#L20-L39) uses Node 24, so an old-tooling assumption would also be wrong. Java-style translation scaffolding and the single-result boundary remain maintenance and feature trade-offs.

The sibling [browser media lifecycle](https://github.com/zxing-js/browser/blob/9ad027d88d4533bd6d29f9d8d7e517e23cd361ff/src/readers/BrowserCodeReader.ts#L643-L754) handles start failure, stop, constraints, capabilities, and torch controls. Its [scan loop](https://github.com/zxing-js/browser/blob/9ad027d88d4533bd6d29f9d8d7e517e23cd361ff/src/readers/BrowserCodeReader.ts#L1009-L1095) reuses a canvas and cancels scheduled work, but decoding stays on the calling thread. The inspected [browser tests](https://github.com/zxing-js/browser/blob/9ad027d88d4533bd6d29f9d8d7e517e23cd361ff/test/readers/qr-code-reader.test.ts#L7-L23) use Node image and canvas facilities, rather than a real browser-camera matrix.

**OpenCV and WeChat.** The sampled [OpenCV implementation](https://github.com/opencv/opencv/blob/b3d14b1caf41abb74d101a898b1fcae841152a24/modules/objdetect/src/qrcode.cpp#L2842-L3008) has its own decoder and curved-image processing. Its [multi-code flow](https://github.com/opencv/opencv/blob/b3d14b1caf41abb74d101a898b1fcae841152a24/modules/objdetect/src/qrcode.cpp#L4090-L4190) is real implementation, but UTF16BE is rejected and ECI support is explicitly incomplete. The large implementation and wider module dependencies cost more to understand and package. WeChat adds an optional [neural detector and super-resolution pipeline](https://github.com/opencv/opencv_contrib/blob/b67a855188a3d683813731010f6d39ac614733a4/modules/wechat_qrcode/src/wechat_qrcode.cpp#L39-L182), with [several binarisers](https://github.com/opencv/opencv_contrib/blob/b67a855188a3d683813731010f6d39ac614733a4/modules/wechat_qrcode/src/decodermgr.cpp#L21-L61), DNN dependencies, and downloaded model configuration. Its [regression test](https://github.com/opencv/opencv_contrib/blob/b67a855188a3d683813731010f6d39ac614733a4/modules/wechat_qrcode/test/test_qrcode.cpp#L14-L100) contains exclusions and commented-out model initialisation. That supports further difficult-image evaluation, not an unmeasured accuracy claim or a default second engine.

**paulmillr/qr.** The decoder owns [reusable scan arenas](https://github.com/paulmillr/qr/blob/951806df842fb7c9214012a73b00e60b259243d3/src/decode.ts#L1311-L1349), and its [public operations](https://github.com/paulmillr/qr/blob/951806df842fb7c9214012a73b00e60b259243d3/src/decode.ts#L3100-L3174) provide synchronous, cooperative asynchronous, batch, and multiple-symbol paths with cleanup. Cooperative asynchronous execution still uses the current thread. [Ownership tests](https://github.com/paulmillr/qr/blob/951806df842fb7c9214012a73b00e60b259243d3/test/decode.test.ts#L111-L162) and [asynchronous failure tests](https://github.com/paulmillr/qr/blob/951806df842fb7c9214012a73b00e60b259243d3/test/decode-async.test.ts#L12-L100) are meaningful strengths. The 3,457-line decoder is dense, and [payload handling](https://github.com/paulmillr/qr/blob/951806df842fb7c9214012a73b00e60b259243d3/src/decode.ts#L286-L358) rejects modes outside Numeric, Alphanumeric, Byte, and ECI. No Micro QR or rMQR path was found. Its delegated CI workflow was not audited, so its runtime matrix remains unverified here.

**ZBar and zbar-wasm.** The WASM wrapper [pins ZBar 0.23.90](https://github.com/undecaf/zbar-wasm/blob/c04ab59682681e27a24b36b36084806437a5d224/Makefile#L1-L14), so newer upstream work cannot be credited to that artifact. Typed [scanner ownership](https://github.com/undecaf/zbar-wasm/blob/c04ab59682681e27a24b36b36084806437a5d224/src/ZBarScanner.ts#L7-L46), [memory tests](https://github.com/undecaf/zbar-wasm/blob/c04ab59682681e27a24b36b36084806437a5d224/tests/30-memory.test.ts#L5-L45), and [format tests](https://github.com/undecaf/zbar-wasm/blob/c04ab59682681e27a24b36b36084806437a5d224/tests/60-ZBarScanner.test.ts#L4-L41) are useful evidence. However, its [convenience scan flow](https://github.com/undecaf/zbar-wasm/blob/c04ab59682681e27a24b36b36084806437a5d224/src/module.ts#L14-L63) destroys the image only after successful awaited work, leaving an inferred exception-path leak. The pinned core [supports standard QR payload modes and multiple symbols](https://github.com/mchehab/zbar/blob/24e9739746b6f5bf2bca15ccdb47210a76153a77/zbar/qrcode/qrdec.h#L15-L149), with no Micro QR or rMQR implementation found. Chromium-oriented wrapper testing does not establish a broad device matrix.

**quirc.** Its [create, resize, decode, and destroy API](https://github.com/dlbeer/quirc/blob/f2e4271ae43a15d9263704e07bc86cba5697d74d/lib/quirc.h#L32-L66) and [overflow-aware resize implementation](https://github.com/dlbeer/quirc/blob/f2e4271ae43a15d9263704e07bc86cba5697d74d/lib/quirc.c#L36-L163) give it clear ownership and a small maintenance surface. Multiple detected symbols and mirrored retries are supported. The [decoder](https://github.com/dlbeer/quirc/blob/f2e4271ae43a15d9263704e07bc86cba5697d74d/lib/decode.c#L840-L902) handles standard QR versions and several payload modes. Its [image runner](https://github.com/dlbeer/quirc/blob/f2e4271ae43a15d9263704e07bc86cba5697d74d/tests/qrtest.c#L109-L149) counts decoding successes without golden-payload assertions in the inspected flow, while an [overflow regression test](https://github.com/dlbeer/quirc/blob/f2e4271ae43a15d9263704e07bc86cba5697d74d/tests/overflow_test.c#L22-L27) checks arithmetic. No CI workflow or browser binding was found in the audited archive. Its lower total reflects integration and verification gaps, rather than excessive core complexity.

**jsQR.** Its [locate, extract, and decode pipeline](https://github.com/cozmo/jsQR/blob/49a9633931fb8030ac2fc9cecc121d6e5a19f9a3/src/index.ts#L29-L83) is readable, with raw bytes, locations, and chunk metadata. The same entry point mutates shared defaults and selects an inverted matrix without allocating it for `onlyInvert`. A targeted execution against the published package confirmed that failure. [Payload handling](https://github.com/cozmo/jsQR/blob/49a9633931fb8030ac2fc9cecc121d6e5a19f9a3/src/decoder/decodeData/index.ts#L37-L46) includes Kanji and ECI but leaves structured append and FNC1 commented out. It returns one symbol. [Exact-output fixture tests](https://github.com/cozmo/jsQR/blob/49a9633931fb8030ac2fc9cecc121d6e5a19f9a3/tests/end-to-end-test.ts#L7-L16) are a strength, while [Node 6/8/10 CI](https://github.com/cozmo/jsQR/blob/49a9633931fb8030ac2fc9cecc121d6e5a19f9a3/.travis.yml#L1-L13) and the old TypeScript/Jest/Webpack stack create a concrete tooling burden. No Micro QR or rMQR implementation was found.

**cam2qr** is the strongest camera-lifecycle reference in this sample because [ownership and teardown](https://github.com/Datawalke/cam2qr/blob/2219ecab8d46acfa18db8125c9ca8c4985c703f3/src/scanner/scanner.ts#L221-L373) separate acquisition, scanning, the decode runner, and adapters, with [race regression tests](https://github.com/Datawalke/cam2qr/blob/2219ecab8d46acfa18db8125c9ca8c4985c703f3/test/scanner/teardown-race.test.ts#L34-L146). Its [frame loop](https://github.com/Datawalke/cam2qr/blob/2219ecab8d46acfa18db8125c9ca8c4985c703f3/src/scanner/scanner.ts#L473-L544) awaits decoding before scheduling more work, supports multiple QR results, and assembles structured append. [CI](https://github.com/Datawalke/cam2qr/blob/2219ecab8d46acfa18db8125c9ca8c4985c703f3/.github/workflows/ci.yml#L8-L36) includes a Chromium fake-camera test. Limits remain: the committed corpus has four synthetic images, native-detector mode supplies placeholder QR metadata, hidden-page pause retains the stream, and post-decode state checks do not establish generation ownership across stop/restart. Adopting it would also choose an independently implemented decoder whose recognition quality was not deeply audited here.

**React QR Scanner** has clear hook, component, and type boundaries, a [serialised camera queue](https://github.com/yudielcurbelo/react-qr-scanner/blob/8c7ef45964607859468ef6ba18b98d717445b7a8/src/hooks/useCamera.ts#L126-L248), and [camera regression tests](https://github.com/yudielcurbelo/react-qr-scanner/blob/8c7ef45964607859468ef6ba18b98d717445b7a8/src/hooks/useCamera.test.tsx#L100-L149). It uses a detector ponyfill rather than a new core, with controls, multiple results, and overlays. However, the [startup ownership window](https://github.com/yudielcurbelo/react-qr-scanner/blob/8c7ef45964607859468ef6ba18b98d717445b7a8/src/hooks/useCamera.ts#L49-L97) can leave an acquired stream outside published ownership if play fails, and the [awaited scan flow](https://github.com/yudielcurbelo/react-qr-scanner/blob/8c7ef45964607859468ef6ba18b98d717445b7a8/src/hooks/useScanner.ts#L75-L177) lacks a cancellation-generation check. Its React ownership model and camera-only public surface make it a less direct LiveView camera/file fit.

**barcode-engine** has coherent camera, decoder, consensus, React, and demo boundaries. Its [native detector gate](https://github.com/taeyunekim-chris/barcode-engine/blob/61b948ac15ef7c0240c9107aa100c1642bbf95b7/packages/core/src/decoder/native.ts#L26-L56) checks requested formats and actual operation, while the [frame loop](https://github.com/taeyunekim-chris/barcode-engine/blob/61b948ac15ef7c0240c9107aa100c1642bbf95b7/packages/core/src/engine.ts#L281-L340) bounds dimensions, serialises ordinary decoding, and rejects stale frame generations. Its [ZXing options](https://github.com/taeyunekim-chris/barcode-engine/blob/61b948ac15ef7c0240c9107aa100c1642bbf95b7/packages/core/src/decoder/zxing-shared.ts#L5-L35) limit results to one, and [consensus](https://github.com/taeyunekim-chris/barcode-engine/blob/61b948ac15ef7c0240c9107aa100c1642bbf95b7/packages/core/src/internal/consensus.ts#L41-L66) is count-based, not calibrated recognition confidence. Committed core tests cover frame and consensus logic, leaving camera acquisition/disposal races less established. Its reusable scope is useful, but overlaps ownership the Phoenix hook still needs.

**html5-qrcode** is a credible complete embeddable UI when its controls match the product. Its [decoder composition](https://github.com/mebjas/html5-qrcode/blob/d505e505022cbb6680e6c8babd964e3be9a2d586/src/code-decoder.ts#L38-L97) combines vendored ZXing JS and native detection, with camera/file selection, zoom, torch, and barcode formats. The [camera loop](https://github.com/mebjas/html5-qrcode/blob/d505e505022cbb6680e6c8babd964e3be9a2d586/src/html5-qrcode.ts#L1166-L1235) schedules after decoding, but apparent asynchronous ZXing work remains synchronous on the main thread. [Start](https://github.com/mebjas/html5-qrcode/blob/d505e505022cbb6680e6c8babd964e3be9a2d586/src/html5-qrcode.ts#L410-L465) and [stop](https://github.com/mebjas/html5-qrcode/blob/d505e505022cbb6680e6c8babd964e3be9a2d586/src/html5-qrcode.ts#L546-L592) do not provide simple cancellation during a pending permission prompt. One result per decode and [Node 16 CI](https://github.com/mebjas/html5-qrcode/blob/d505e505022cbb6680e6c8babd964e3be9a2d586/.circleci/config.yml#L6-L21) are concrete feature and verification limits.

**Nimiq QR Scanner** is a compact framework-neutral alternative with image input, cropping, overlays, camera switching, and flash. Its [awaited loop](https://github.com/nimiq/qr-scanner/blob/abcfe1bce2703721408d8ce7ebde94a359998506/src/qr-scanner.ts#L793-L867) supplies ordinary backpressure and uses video-frame callbacks when available. Its [lifecycle](https://github.com/nimiq/qr-scanner/blob/abcfe1bce2703721408d8ce7ebde94a359998506/src/qr-scanner.ts#L329-L412) releases hidden-page capture after a delay and terminates workers on destroy. It lacks an acquisition generation and a post-decode active check, returns one QR result, and has [build scripts without a test script](https://github.com/nimiq/qr-scanner/blob/abcfe1bce2703721408d8ce7ebde94a359998506/package.json#L21-L23), with no test suite or CI workflow found in the pinned source.

**Vue Qrcode Reader** offers clean camera, file, and drop components with multi-result arrays and explicit camera events. Its [component lifecycle](https://github.com/gruhn/vue-qrcode-reader/blob/3cd37a11ab86e213f5794f390cc761f222cf3208/src/components/QrcodeStream.vue#L190-L268) checks mount state and requests camera stop on unmount. However, the [camera module](https://github.com/gruhn/vue-qrcode-reader/blob/3cd37a11ab86e213f5794f390cc761f222cf3208/src/misc/camera.ts#L29-L126) shares queue and detector state across instances, and its [stop flow](https://github.com/gruhn/vue-qrcode-reader/blob/3cd37a11ab86e213f5794f390cc761f222cf3208/src/misc/camera.ts#L202-L250) waits for a video error without a bounded timeout before stopping tracks. No test suite was found, and [release CI](https://github.com/gruhn/vue-qrcode-reader/blob/3cd37a11ab86e213f5794f390cc761f222cf3208/.github/workflows/main.yml#L22-L41) primarily builds and type-checks. Vue-specific state adds integration work for LiveView.

**RECQR** is the broadest browser-product reference in this sample for upload, drop, paste, content parsing, action cards, and history. Its [file-image pipeline](https://github.com/flessan/RECQR/blob/5c87b3fb5054cddf6b56664b423286b9fa138d38/src/lib/qr/imageDecoder.ts#L33-L120) tries bounded scales and crops, but the [video path](https://github.com/flessan/RECQR/blob/5c87b3fb5054cddf6b56664b423286b9fa138d38/src/lib/hooks/useCameraScanner.ts#L428-L447) separately allocates canvases and handles only non-inverted input. Its [acquisition and loop](https://github.com/flessan/RECQR/blob/5c87b3fb5054cddf6b56664b423286b9fa138d38/src/lib/hooks/useCameraScanner.ts#L198-L302) leave late acquisition and competing asynchronous work concerns. Parser/security tests exist, but positive image and camera-lifecycle coverage is weak, and deployment CI builds without running Vitest. Use its result presentation as a reference rather than copying its camera ownership.

**QR Snapper** has useful worker initialisation, timeout recovery, single-request gating, hidden-page handling, and [testable camera ownership](https://github.com/PaulKinlan/qrcode/blob/a8504c33adbb512026769e4c96adb9dd1292e17d/app/scripts/components/camera/WebCamManager.js#L20-L42). Its [worker client](https://github.com/PaulKinlan/qrcode/blob/a8504c33adbb512026769e4c96adb9dd1292e17d/app/scripts/qrclient.js#L98-L131) and [result restrictions](https://github.com/PaulKinlan/qrcode/blob/a8504c33adbb512026769e4c96adb9dd1292e17d/app/scripts/components/dialogs/QRCodeManager.js#L155-L174) explain the engineering/feature split: it discards ordinary text, Wi-Fi, and vCard payloads because its product is URL-oriented. Camera visibility and URL utility tests passed locally, but overlapping acquisition generations and real browser decoding were not validated. It is a useful worker/recovery reference rather than a general payload scanner contract.

**QR Code Enhance** combines ZXing WASM, image tracking, perspective recovery, and a WeChat wrapper, rather than introducing another core. Its [frame gates](https://github.com/connectedGraph/qr-code-enhance/blob/5de60842177ea81aa9a8f5e1193d9abc3c1eb8ba/src-v3/main.ts#L607-L640) control ordinary and deeper processing, and [result rendering](https://github.com/connectedGraph/qr-code-enhance/blob/5de60842177ea81aa9a8f5e1193d9abc3c1eb8ba/src-v3/main.ts#L791-L869) uses text and explicit HTTP(S) links. A large v3 entry, retained older implementations, no discovered behavioural tests, and [beforeunload-only cleanup](https://github.com/connectedGraph/qr-code-enhance/blob/5de60842177ea81aa9a8f5e1193d9abc3c1eb8ba/src-v3/main.ts#L1554-L1563) lower maintainability. Its [deep detector](https://github.com/connectedGraph/qr-code-enhance/blob/5de60842177ea81aa9a8f5e1193d9abc3c1eb8ba/src-v3/deep-detector.ts#L73-L122) still invokes WeChat on the main thread. It supplies experiments worth comparing against difficult images, without establishing better accuracy.

**Curium** has broad payload parsing and mobile action handling, but its [scanner](https://github.com/nylxar/curium/blob/214bfca5fd029a2c03d3be2e6aff3083efe2992f/app/scan.tsx#L10-L21) uses a React Native camera dependency and Android/iOS permissions. Its [result flow](https://github.com/nylxar/curium/blob/214bfca5fd029a2c03d3be2e6aff3083efe2992f/app/scan.tsx#L139-L226) selects the first gallery result. The desktop implementation is a generator, and the [Android workflow](https://github.com/nylxar/curium/blob/214bfca5fd029a2c03d3be2e6aff3083efe2992f/.github/workflows/android-test-build.yml#L32-L60) builds an APK rather than testing scanner behaviour. Its lower P score concerns scanner coverage across platforms, not the ability to produce multiple application builds. Treat it as native UX reference, with a materially different AGPL licence.

**antfu/qr-scanner-wechat** must be distinguished from the sampled upstream engine. Its [wrapper](https://github.com/antfu/qr-scanner-wechat/blob/1e22e41273539a1e4b777cf2bb8e2e8f0158d09f/src/index.ts#L50-L92) caches native state, returns only `res.get(0)`, and omits cleanup for several native result objects and failure paths. Its [test](https://github.com/antfu/qr-scanner-wechat/blob/1e22e41273539a1e4b777cf2bb8e2e8f0158d09f/test/index.test.ts#L8-L22) covers one successful fixture. A pinned upstream build recipe for its bundled OpenCV artifacts was not established, so improvements in the sampled OpenCV source cannot be assigned to this package. The leak concern is source-derived, not heap-measured.

**Koder** demonstrates React/ZBar WASM packaging, but its [capture loop](https://github.com/maslick/koder/blob/6f8bebd2ad454ed5320b6519cb932cc52a4af9fa/src/components/scan.js#L75-L191) can schedule competing animation-frame work and posts frames without an acknowledgement gate. Manual stop does not terminate the worker, and no component-unmount or hidden-page teardown was found. Its [build workflow](https://github.com/maslick/koder/blob/6f8bebd2ad454ed5320b6519cb932cc52a4af9fa/.github/workflows/pr.yml#L8-L64) uses an unpinned WASM Docker tag and old Node tooling without behavioural tests. Those are reasons to retain it as historical packaging reference rather than a lifecycle foundation.

**Rxing.** Its [dirty CPU entry point](https://github.com/ivan-podgurskiy/rxing/blob/6679af8f8c178700d33cb0d27c8d9efc40c461ac/native/rxing_nif/src/lib.rs#L55), separate decode/options/results modules, and [pre-decode image limits](https://github.com/ivan-podgurskiy/rxing/blob/6679af8f8c178700d33cb0d27c8d9efc40c461ac/native/rxing_nif/src/decode.rs#L15) make it the strongest independent backend fit. The [public API](https://github.com/ivan-podgurskiy/rxing/blob/6679af8f8c178700d33cb0d27c8d9efc40c461ac/lib/rxing.ex#L29) accepts encoded binaries or files and exposes QR, Data Matrix, Code 128, and EAN-13, with multiple results, bytes, points, and metadata. [Integration tests](https://github.com/ivan-podgurskiy/rxing/blob/6679af8f8c178700d33cb0d27c8d9efc40c461ac/test/rxing/integration_test.exs#L1), concurrency/property tests, and [Linux/macOS CI](https://github.com/ivan-podgurskiy/rxing/blob/6679af8f8c178700d33cb0d27c8d9efc40c461ac/.github/workflows/ci.yml#L10) support the engineering score. It requires Rust compilation and has no inspected Windows CI or precompiled loader. Its four exposed formats should not be confused with every format implemented upstream.

**image_qrcode.** The [Vix image API](https://github.com/elixir-image/image_qrcode/blob/160967b7b6e1c56f5961beab3eca4301c0091b41/lib/image/qrcode.ex#L134) owns grayscale conversion, and its [per-call quirc context](https://github.com/elixir-image/image_qrcode/blob/160967b7b6e1c56f5961beab3eca4301c0091b41/c_src/qrcode_nif.c#L147) detects multiple codes, retries mirrored input, returns payload bytes and metadata, and frees native state. Both NIFs are marked dirty CPU. [Behaviour tests](https://github.com/elixir-image/image_qrcode/blob/160967b7b6e1c56f5961beab3eca4301c0091b41/test/image_qrcode_test.exs#L36), [concurrency tests](https://github.com/elixir-image/image_qrcode/blob/160967b7b6e1c56f5961beab3eca4301c0091b41/test/concurrency_test.exs#L25), and CI support its engineering score. The [precompiler configuration](https://github.com/elixir-image/image_qrcode/blob/160967b7b6e1c56f5961beab3eca4301c0091b41/mix.exs#L117) covers Linux and macOS but leaves the Windows compiler map empty. It adds Vix and an image-buffer copy, with no package-level maximum image budget in the inspected decode entry.

**Evision.** Its [QR test](https://github.com/cocoa-xu/evision/blob/3ff84da482b5d17d0756c37633af506a5c42c910/test/qr_detector_test.exs#L6) asserts decoded text, corner points, and the rectified matrix through generated OpenCV bindings. [Native dispatch](https://github.com/cocoa-xu/evision/blob/3ff84da482b5d17d0756c37633af506a5c42c910/c_src/evision.cpp#L30) distinguishes dirty CPU and IO work, while [version and target configuration](https://github.com/cocoa-xu/evision/blob/3ff84da482b5d17d0756c37633af506a5c42c910/mix.exs#L1) provides wider platform packaging. However, [Windows CI](https://github.com/cocoa-xu/evision/blob/3ff84da482b5d17d0756c37633af506a5c42c910/.github/workflows/windows-x86_64.yml#L157) runs an explicit numeric/safety subset and comments out the broad suite. Windows QR behaviour remains unverified. This is useful when OpenCV is already needed, but brings a much wider native surface for QR scanning alone.

**QQR.** The [pure Elixir pipeline](https://github.com/dannote/qqr/blob/43a17684099bf7ceba258b104986cf7d21563764/lib/qqr.ex#L115) has clear binariser, locator, extractor, Reed-Solomon, and data-decoder modules, with [synthetic matrix and RGBA tests](https://github.com/dannote/qqr/blob/43a17684099bf7ceba258b104986cf7d21563764/test/qqr/battle_test.exs#L47). It accepts raw RGBA or rectified module grids, returns the first successful symbol, and avoids native packaging. However, `:only_invert` selects a matrix that its [binariser never creates](https://github.com/dannote/qqr/blob/43a17684099bf7ceba258b104986cf7d21563764/lib/qqr/binarizer.ex#L95), so that option always fails by inspected control flow. [Kanji decoding](https://github.com/dannote/qqr/blob/43a17684099bf7ceba258b104986cf7d21563764/lib/qqr/data_decoder.ex#L225) returns empty text with bytes, and ECI assignments are discarded. Per-pixel lists and tuples also prevent assuming a small memory footprint from the absence of NIFs. These defects were source-derived, not executed here.

**QRex.** Its [native entry](https://github.com/brandonhamilton/qrex/blob/539103d62f37f491b246d8929404b3973c17132c/native/qrex/src/lib.rs#L20) loads an image, clones it for sequential rxing, rqrr, and bardecoder attempts, and returns the first engine with any success. That is genuine fallback, but does not combine detections. It uses a regular scheduler annotation and has no explicit image budget in that entry. The [release workflow](https://github.com/brandonhamilton/qrex/blob/539103d62f37f491b246d8929404b3973c17132c/.github/workflows/release.yml#L17) configures broad native targets, while the inspected repository has only an ExUnit bootstrap and no recognition tests. Those build targets do not establish runtime reliability.

**zbar Elixir wrapper.** Its [Port-based scan flow](https://github.com/elixir-vision/zbar-elixir/blob/7c319ef1d4316b3610abfa1979bae3b93fbf3672/lib/zbar.ex#L26) isolates native decoding in an external process and supports a timeout. However, every caller writes the same `zbar_image.jpg` temporary path, so concurrent scans can replace each other's input. The API accepts JPEG only, [builds against system ZBar and JPEG libraries](https://github.com/elixir-vision/zbar-elixir/blob/7c319ef1d4316b3610abfa1979bae3b93fbf3672/Makefile#L9), and has a [non-scanning arithmetic test](https://github.com/elixir-vision/zbar-elixir/blob/7c319ef1d4316b3610abfa1979bae3b93fbf3672/test/zbar_test.exs#L5). No Windows build path or CI was found.

**rqrr_ex and bardecoder_ex.** Their [rqrr](https://github.com/denvera/rqrr_ex/blob/aef797e684cdde847377c310d1154715e4899104/native/rqrr_ex_nif/src/lib.rs#L20) and [bardecoder](https://github.com/denvera/bardecoder_ex/blob/7676df21fca213d05c0804924cfd2265d382b5fd/native/bardecoder_ex_nif/src/lib.rs#L65) entries expose image-binary QR detection and metadata, but use regular scheduler annotations and Rustler 0.27 source builds. Their [rqrr test](https://github.com/denvera/rqrr_ex/blob/aef797e684cdde847377c310d1154715e4899104/test/rqrr_ex_test.exs#L5) and [bardecoder test](https://github.com/denvera/bardecoder_ex/blob/7676df21fca213d05c0804924cfd2265d382b5fd/test/bardecoder_ex_test.exs#L5) call nonexistent `hello/0` functions. No platform CI or licence file was found in either snapshot. The source-present decoding flow does not compensate for those adoption gaps.

## Existing OpenQR ownership

At the research baseline, the web project already depended on `../openqr/bindings/elixir` in [mix.exs](../mix.exs), and its installed `qr_code` 3.2.0 dependency was an encoder. No external decoder package was present in that baseline. The accompanying implementation now pins `zxing-wasm` 3.1.7 in [assets/package.json](../assets/package.json). The backend dependency set has not gained another decoder.

The sibling engine's [native dependency configuration](../../openqr/cmake/Dependencies.cmake) enables ZXing readers, disables writers and non-QR formats, and pins `f19f7c6e0509fe0eeb822bf35c41b0f637dec290`. Its private [verify_frames implementation](../../openqr/src/engine.cpp) wraps RGBA frames in `ZXing::ImageView`, tries two binarisers, calls `ReadBarcodes`, and compares payload bytes. Its [image loader](../../openqr/src/image.cpp) already handles PNG, GIF, WebP, ICO, and JPEG. The [Elixir binding](../../openqr/bindings/elixir/lib/openqr/engine.ex) and [NIF export table](../../openqr/bindings/elixir/c_src/openqr_nif.c) expose generation, styles, and previews only. These are current local source observations, not an already available scanner API.

For backend scanning, consolidate recognition and image ownership inside that engine, then expose decoded payloads and positions through its existing C boundary and dirty CPU NIF. Keeping verification and scanning on one owned implementation avoids another image stack and native decoder dependency. Additional barcode formats would need an intentional change to the native build configuration and their own validation. The current native CI matrix does not validate a scanner endpoint that does not yet exist.

## Integration decision

| Path | Consequence for this application |
|---|---|
| Browser camera frames decoded in a worker | Camera permission, stream lifetime, sampling, and worker lifetime belong to the LiveView hook. Frames remain local, and the worker keeps synchronous decoding away from the UI thread |
| Browser-selected image decoded locally | The same reader can accept a Blob or pixel input. No server image transport is needed for an ordinary scan |
| Uploaded image decoded by the native engine | Reuses the existing backend decoder and image stack, but requires an exposed API, upload handling, and bounded native work |
| Continuous browser frames sent to Elixir | Still requires browser camera code, plus encoding, transport, round trips, server CPU, and concurrent memory decisions. No inspected Elixir package provides that complete browser flow |

For scale, one 1280 x 720 RGBA frame contains 3,686,400 bytes before transport. QQR requires raw RGBA, while Rxing, QRex, rqrr_ex, and bardecoder_ex can accept encoded images. Compression changes transfer size but adds work. This arithmetic explains the transport distinction without claiming measured latency. Dirty CPU scheduling preserves normal BEAM scheduler availability but neither isolates native crashes nor caps total concurrent memory.

The accompanying [worker](../assets/js/qr_scanner_worker.js) uses the existing `zxing-wasm/reader` API directly, restricts formats to `QRCode`, and requests plain text output. Like OpenQR's native verifier, it tries both LocalAverage and GlobalHistogram binarisation. Integration testing found a real styled export that only the second method decoded. The worker combines valid results from both passes and merges overlapping detections of the same text while preserving equal payloads at separate positions. This adds decoding work per frame, so capture waits for completion before scheduling another frame. It returns decoded text and format to the UI. The upstream [result API](https://github.com/Sec-ant/zxing-wasm/blob/1a2b5310056a2b140feb6ca625fcefd6eaf12ef0/src/bindings/readResult.ts#L13-L110) also exposes bytes, positions, mirrored or inverted state, and structured-append metadata, but those are underlying capabilities rather than fields currently presented by OpenQR.

The [LiveView hook](../assets/js/qr_scanner.js) owns camera start and stop, one awaited frame decode at a time, delayed subsequent capture, stale-generation checks, track cleanup, and worker termination. The [asset build](../config/config.exs) packages the worker and reader WASM for local serving. The Scan panel provides camera capture and image files through the shared file input, including its drag-and-drop behaviour. It does not provide paste, screen capture, camera switching, torch controls, or a backend upload path. Browser image decoding uses a still frame, so animated-image support does not mean every animation frame is scanned. A complete scanner wrapper remains preferable if future required controls match its existing UI closely enough to justify adopting its state and lifecycle.

## Strongest counterarguments

1. A small custom hook still owns real media-browser complexity. A proven scanner wrapper can reduce that work, especially around camera selection and mobile recovery. The decision should change if its source meets the required lifecycle and UI without awkward adaptation.
2. Pure JavaScript avoids a separate WASM asset and its loading or memory lifecycle. paulmillr/qr and zxing-js are credible alternatives if that deployment constraint outweighs the broader engine and ownership evidence for zxing-wasm.
3. OpenCV or WeChat could recognise an important class of difficult images better. Their different detection and preprocessing paths make that plausible, but only a representative comparison corpus can establish it for OpenQR. Do not add an unconditional fallback engine on that assumption.
4. Reusing the native engine centralises decoding and avoids another browser payload. That is reasonable for occasional uploads, but continuous camera transport still needs browser work and imposes server work per frame.
5. Sharing ZXing between generation verification and browser scanning is coherent engineering, but does not test compatibility with independent phone-camera decoders. Keep independent-reader validation when evaluating generated QR designs.

## Verification performed and remaining limits

The research executed a targeted check against the published jsQR 1.4.0 package through mise-managed Node. On a blank 40 x 40 RGBA image, `attemptBoth` returned `null`, while `onlyInvert` threw `TypeError: Cannot read properties of undefined (reading 'height')`. This confirms one regression path, not QR recognition quality or throughput. Source SHA256 comparisons also confirmed correspondence for the untagged Elixir package snapshots described above.

QR Snapper's `camera-visibility.test.mjs` and `url-utils.test.mjs` were executed through mise-managed Node: 16 tests passed, with no failures or skips. These exercise mocked visibility/camera ownership and URL utilities. They do not establish positive image decoding, a full application build, or real browser and camera operation.

OpenQR integration verification passed the full 347-test Elixir suite and the 232-test JavaScript suite, including 13 scanner tests and four download-history tests. The scanner tests exercise the shipped reader WASM with multiple generated symbols, rotation, inversion, plain-text line breaks, a no-code image, and a real styled OpenQR PNG that requires GlobalHistogram. Lifecycle tests use mocked media streams and deferred image decoding to check cancellation, frame backpressure, track release, local result rendering, and blob URL cleanup. Worker tests also distinguish equal payloads at separate positions from duplicate detections across binarisation passes. These checks do not affect the source-review scores.

Browser checks in the in-app Chromium browser confirmed successful scanning of actual OpenQR PNG and SVG exports, no-code feedback for a logo image, file clearing, history remaining empty before a download, exact export entries appearing after PNG and SVG download actions, persistence across reload, and no extra entries from scans. Clearing history removed the test entries. A browser-specific SVG failure in `createImageBitmap` led to one native `Image.decode()` flow for all selected image formats, with the image source and blob URL released on cancellation and completion. At the time of these checks, file input was limited to 25 MiB, source images to 64 million pixels, file canvases to a 2560-pixel longest edge, and camera canvases to 1600 pixels. The source-dimension check happens after native image decoding and does not cap the browser's initial decode allocation. See the [developer README](README.md) for current file size and history behavior.

No upstream full test suite, fresh decoder build from the inspected snapshots, physical browser-camera session, recognition benchmark, peak-memory benchmark, or cross-device browser matrix was executed during this review. The chosen published WASM binary was executed, and OpenQR's application assets were built. Source-inferred resource leaks, scheduler concerns, and QQR control-flow defects are identified as such. Existing upstream tests and CI files were read as engineering evidence, except for the specific executed checks listed above.

Before production rollout, extend validation to representative user photographs, damaged codes, animated images where required, and the actual supported browsers and devices. Check physical camera start, stop, permission refusal, page destruction, and repeated scans. Camera switching needs its own implementation and validation if added. That evaluation can revise this recommendation without changing the source findings above.

In practical terms, the decoder reads the symbol, while the hook operates the camera. Scanning a QR code printed on a receipt should normally keep camera frames in the browser and send only the decoded value to application behaviour. Uploading a saved image can use the same browser reader, with backend decoding reserved for a requirement that needs it.
